# Policy and reporting

This guide ties the scanner's policy controls to its report formats. It covers
the configuration schema, the order in which policy decisions are applied,
waivers with expiry, every report format, CI examples, and the limits of what a
report can tell you.

For the command-line reference see [CLI](cli.md); for every configuration field
see [Configuration](configuration.md).

## Policy schema

Policy lives in `soroban-scan.toml` next to the scan root (or in the file given
with `--config`). Repository-provided configuration is untrusted data: it can
never execute code or enable network access.

```toml
min_severity = "info"
min_confidence = "low"
exclude = ["vendor/**"]
exclude_tests = false

# Hash selected report fields at render time. Presentation-only.
redact = ["finding.evidence", "finding.location.file"]

[rules]
# Rules never run.
disabled = ["SS-007"]
# If non-empty, only these rules run.
enabled = []
# Category filters; an unknown category is a usage error.
disabled_categories = []
enabled_categories = []
# Per-rule overrides.
severity_overrides = { "SS-010" = "medium" }
confidence_overrides = {}

# Path- and rule-scoped suppression. Every entry is reported, even unused ones.
[[suppressions]]
path = "src/generated/**"
rule = "all"
reason = "generated by the SDK"

# Time-limited, owned suppression. Expiry restores the finding to the gate.
[[waivers]]
path = "src/legacy/**"
rule = "SS-001"
owner = "security-team"
reason = "migration tracked in SEC-42"
expires = "2026-12-31"
```

CLI flags override the file for the same setting: `--min-severity`,
`--min-confidence`, `--exclude`, `--exclude-tests`, `--include-cfg-test`,
`--disable`, `--rule`, `--redact`, and `--fail-on`. `--no-config` ignores
discovery entirely. `config show` prints the effective configuration and
`config validate` rejects unknown fields, rule ids, categories, redaction
fields, malformed suppressions, and malformed waivers before a scan runs.

The failure gate is separate from the severity filter:

- `--min-severity` / `--min-confidence` decide which findings are **reported**.
- `--fail-on` (default `high`) decides which reported findings **fail the run**
  with exit code `1`. `--fail-on none` disables the gate.
- `--status-gate FILE` records that same decision as `success`, `failure`, or
  `neutral` for a pull request check. See
  [Policy status gate](cli.md#policy-status-gate).

## Precedence

Policy is applied in this order. Earlier steps win when two controls target the
same finding.

1. **Rule selection.** Disabled rules and disabled categories skip the rule
   entirely. When `rules.enabled` or `rules.enabled_categories` is non-empty it
   is an allow-list. Skipped rules produce no findings at all.
2. **Overrides.** `severity_overrides` and `confidence_overrides` replace a
   rule's defaults before filtering.
3. **Reporting filters.** `min_severity` and `min_confidence` drop findings from
   the report and therefore from the gate.
4. **Inline suppressions.** `// soroban-scan: ignore SS-XXX -- reason` removes
   the anchored finding or item from the gate but keeps it in the report.
5. **Configured suppressions.** `[[suppressions]]` entries apply after inline
   directives, so an inline directive always takes precedence. Every configured
   entry is listed, including entries that match nothing.
6. **Waivers.** `[[waivers]]` entries apply after configured suppressions. An
   unexpired waiver excludes matching findings from the gate and records its
   owner and expiry. An expired waiver suppresses nothing, emits a `CONFIG-003`
   error, and fails the run unless `--fail-on none` is set. Expired waivers are
   reported even when they match no finding.
7. **Baselines.** With `--baseline`, existing findings are accepted and only new
   findings are gated. `--new-only` changes the report but not the gate;
   `--incremental` only hides resolved findings.
8. **Truncation.** `--max-findings` applies after the gate has seen every
   finding, so a bounded report can never turn a failing scan into a passing one.

Suppressed and waived findings remain in terminal, JSON, SARIF, Markdown, and
HTML reports together with the rule, reason, and source of the suppression.
Nothing is dropped silently. A stale or mistyped suppression is visible because
every entry is reported even when it matched nothing.

## Waivers

A waiver is a suppression with an owner and an expiry date. It must have a
non-empty `owner`, a non-empty `reason`, and a valid UTC `expires` date in
`YYYY-MM-DD` form. Missing or empty fields are configuration errors (exit code
`2`).

```toml
[[waivers]]
path = "src/legacy/**"
rule = "SS-001"
owner = "security-team"
reason = "migration tracked in SEC-42"
expires = "2026-12-31"
```

- `expires` is the **last** day the waiver applies. The comparison uses the UTC
  date of the scan, never the local timezone.
- An unexpired waiver behaves like a suppression: the finding leaves the gate
  and stays in the report with `"source": "waiver"`, `owner`, and `expires`.
- After expiry the finding returns to the gate and a `CONFIG-003` error is
  emitted. The run exits `1` unless `--fail-on none` is given.
- JSON reports include a `waivers` array for every configured entry:

```json
{
  "path": "src/legacy/**",
  "rule": "SS-001",
  "owner": "security-team",
  "reason": "migration tracked in SEC-42",
  "expires": "2026-12-31",
  "expired": false,
  "matched": 1,
  "findings_suppressed": 1,
  "applied": true
}
```

Waivers are for accepted risk with a deadline; use a suppression for generated
or vendored code that will never change, and a baseline for known findings across
a project. See [Waivers with expiry](cli.md#waivers-with-expiry).

## Report formats

Every format reports the same findings, ordering, and exit code. Choose by
consumer, not by content:

| Format | Use it for | Notes |
| ------ | ---------- | ----- |
| `terminal` | Local review | Grouped by file, with severity, evidence, and remediation. `--quiet` prints one line per finding. |
| `json` | Tooling and archives | Stable contract: `schema_version`, `tool`, `project`, `stats`, `effective_config`, `findings`, `suppressed`, `suppressions`, `config_suppressions`, `waivers`, `diagnostics`, optional `baseline` and `truncation`. See [`integration/report.schema.json`](integration/report.schema.json). |
| `sarif` | GitHub code scanning and SARIF viewers | SARIF 2.1.0. Suppressed results stay in `results` and are marked with SARIF `suppressions`. `--sarif-policy` adds opt-in `properties.policyStatus`. |
| `markdown` | Pull requests and documentation | Severity and category summaries plus findings, suppressions, configured suppressions, and waivers. |
| `html` | Reviewer packets and audits | One self-contained file with inline CSS/SVG, no JavaScript, and no remote resources. Includes the `--fail-on` policy block. |
| `github` | GitHub Actions annotations | One escaped `::error`/`::warning`/`::notice` line per finding. Machine output only. |

`--output FILE` writes the report instead of stdout. `--max-findings N` bounds
the report and states the omitted count in every format. `--redact FIELD` hashes
selected fields first; fingerprints, rule ids, and line numbers are never
changed, so `compare` and baselines still match. Redaction is field-scoped only:
it cannot find arbitrary secrets in free-form text, so never treat it as proof
that a report is clean.

Report file names and retention are defined in
[Report retention and artifact naming](retention.md).

## CI examples

Fail a pull request when a new high finding appears:

```yaml
- name: Scan
  run: |
    soroban-scan scan ./contracts \
      --format json --output scan.json \
      --fail-on high --baseline .baseline.json --new-only
```

Upload SARIF to GitHub code scanning:

```yaml
- name: Scan for SARIF
  run: soroban-scan scan ./contracts --format sarif --output results.sarif
- uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: results.sarif
```

Keep a reviewable report artifact with a deterministic name:

```yaml
- name: Name and scan
  run: |
    name=$(soroban-scan artifact-name --project "$GITHUB_REPOSITORY" --commit "$GITHUB_SHA")
    soroban-scan scan ./contracts --format json --output "artifacts/$name"
- uses: actions/upload-artifact@v4
  with:
    name: soroban-scan-report
    path: artifacts/
    retention-days: 30
```

Document a time-limited risk acceptance in the repository configuration:

```yaml
- name: Reject expired waivers
  run: soroban-scan scan ./contracts --format json --fail-on high
```

An expired waiver emits `CONFIG-003` and fails this step even if no finding
crosses the threshold, because the step does not pass `--fail-on none`.

## Policy files

Fail thresholds, report thresholds, and suppressions can live in one versioned
document instead of scattered flags:

```toml
schema_version = 1
fail_on = "high"          # none | info | low | medium | high | critical
min_severity = "low"
min_confidence = "medium"

[[suppressions]]
path = "tests/**"
rule = "SS-001"
reason = "test-only fixture"
```

```bash
soroban-scan scan ./contracts --policy-file soroban-policy.toml
```

- TOML and JSON are supported; the extension selects the parser.
- Unknown keys are errors. `schema_version` must be `1`.
- `fail_on` accepts the same levels as `--fail-on`, plus `none`.
- Suppressions are auditable and use the same path/rule validation as
  configuration.
- Precedence is: built-in defaults < discovered configuration < policy file <
  explicit CLI flags. `--min-severity`, `--min-confidence`, and `--fail-on`
  always win.
- When a policy file is used, the effective policy is printed to stderr:
  `effective policy: fail_on=high min_severity=low min_confidence=medium`.

Per-confidence reporting is controlled by `min_confidence`; per-severity
reporting by `min_severity`. Both are applied deterministically by the engine
before rendering, so the gate and the report always agree.

## Limitations

- The scanner is static: it reports evidence it can see, not runtime behaviour,
  and it never executes, builds, or deploys the code.
- Suppressions and waivers intentionally hide findings from the gate. Their
  value depends on review; every entry is reported so stale ones are visible,
  but the scanner cannot judge whether a reason is honest.
- Waiver expiry is evaluated once per scan against the UTC date. A scan that
  starts before midnight UTC and finishes after it keeps the date it started
  with.
- Fingerprints exclude line numbers, so edited evidence can look like a renamed
  finding in `compare`. Review renamed pairs.
- Redaction covers only the documented fields. It cannot guarantee a report has
  no secrets; keep credentials and environment values out of reports entirely.
- JSON and SARIF are bounded (report size and finding counts) so a hostile input
  cannot exhaust memory. Oversized inputs fail with exit code `3`.
- `--fail-on none` disables both the finding gate and the expired-waiver
  failure; use it only for report-only jobs.
