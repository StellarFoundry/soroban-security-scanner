# Supply-chain verification

This page describes exactly what the project publishes, how to verify a
download, and how dependencies are controlled. It separates what exists today
from what does **not** exist, so a missing signature is not mistaken for an
oversight in the instructions.

## What a release publishes

The release workflow in
[`.github/workflows/publish.yml`](../.github/workflows/publish.yml) publishes,
for a `v*` tag:

| Artifact | What it is | Signed or attested? |
| -------- | ---------- | ------------------- |
| `soroban-scan-<target>.tar.gz` (`.zip` on Windows) | Prebuilt CLI binary for one target | GitHub build-provenance attestation |
| `SHA256SUMS` | SHA-256 digest list for the archives | GitHub build-provenance attestation |
| `soroban-scan.cdx.json` | CycloneDX JSON SBOM for the CLI | Not attested |
| GitHub release notes | The matching `CHANGELOG.md` section | Not signed |
| crates.io packages | `soroban-scan-core` and `soroban-scan-cli` | crates.io registry checksums only |

Targets built by CI:

- `x86_64-unknown-linux-gnu`
- `x86_64-unknown-linux-musl`
- `x86_64-apple-darwin`
- `aarch64-apple-darwin`
- `x86_64-pc-windows-msvc`

There are **no** detached GPG signatures and no cosign signature files for the
published artifacts. The release workflow does not sign the release tag or the
SBOM. The attestations are Sigstore-backed GitHub artifact attestations; they
prove which workflow, commit, and repository produced the subject digest. They
are not a substitute for a detached signature, and the project does not claim
one.

Attestations are created for each archive and for `SHA256SUMS`. The SBOM is
uploaded but not separately attested.

## Verify a download

Download the archive and `SHA256SUMS` from the same GitHub release. Then verify
the checksum.

Linux (GNU coreutils):

```bash
sha256sum --check --ignore-missing SHA256SUMS
```

`--ignore-missing` lets you check one downloaded archive without also
downloading every other platform.

macOS (BSD `shasum` does not support `--ignore-missing`):

```bash
grep 'soroban-scan-aarch64-apple-darwin.tar.gz' SHA256SUMS | shasum -a 256 -c -
```

Replace the filename with the archive you downloaded (`x86_64-apple-darwin` for
Intel Macs).

Windows PowerShell:

```powershell
$archive = "soroban-scan-x86_64-pc-windows-msvc.zip"
$expected = (Select-String -Path .\SHA256SUMS -Pattern $archive).Line.Split(" ")[0]
$actual = (Get-FileHash .\$archive -Algorithm SHA256).Hash.ToLower()
if ($actual -ne $expected) { throw "checksum mismatch for $archive" }
"checksum ok: $actual"
```

If the checksum does not match, stop. Do not extract or run the archive; delete
it and download again from the release page.

## Verify the build provenance

With the [GitHub CLI](https://cli.github.com/) installed and authenticated:

```bash
gh attestation verify soroban-scan-x86_64-unknown-linux-gnu.tar.gz \
  --repo StellarFoundry/soroban-security-scanner
```

Use the archive name you downloaded. For Windows:

```bash
gh attestation verify soroban-scan-x86_64-pc-windows-msvc.zip \
  --repo StellarFoundry/soroban-security-scanner
```

The `--repo` must be the repository that produced the release. If you downloaded
from a fork, use that fork's `owner/name`; an attestation from another repository
will not verify. `gh attestation verify` checks that the artifact digest appears
in an attestation issued by GitHub for a workflow in that repository. It prints
the signer workflow and the source commit when verification succeeds.

## Verify the SBOM

The SBOM is CycloneDX JSON. Download it from the release and confirm the format
before using it in a dependency or vulnerability scanner:

```bash
gh release download v0.2.0 \
  --repo StellarFoundry/soroban-security-scanner \
  --pattern soroban-scan.cdx.json
```

Then inspect `bomFormat` and `specVersion` with the JSON tool you already use
(for example `jq '.bomFormat, .specVersion' soroban-scan.cdx.json`). The SBOM is
informational today: it is generated by `cargo-cyclonedx`, uploaded to the
release, and is **not** attested or signed separately. Do not treat its presence
as proof that the binary matches it; use the archive checksum and attestation for
that.

## Verify the crates.io packages

```bash
cargo install soroban-scan-cli --locked
```

Cargo resolves `soroban-scan-core` at the exact matching version and verifies
the crates.io registry checksum. The release workflow runs
`cargo publish --dry-run` before publishing and publishes core before the CLI.
It does not publish a separate signature for the crate files. If you need to
audit exactly which source was published, compare the crate contents with the
`v*` tag; crates.io exposes the `.crate` archive for each version.

## Dependency policy

Dependencies are governed by
[ADR-0005](architecture/adr/0005-dependency-justification-policy.md). A new or
changed dependency must be necessary, scoped, maintained, licensed, auditable,
justified in the pull request, and reviewed by a maintainer.

The automated gate is `cargo-deny` in CI, configured by
[`deny.toml`](../deny.toml):

- **Advisories:** checked with no ignore list.
- **Licenses:** only the allowlist in `deny.toml` is accepted.
- **Bans:** wildcard version requirements are denied; multiple versions warn.
- **Sources:** the crates.io registry is the only allowed registry; unknown
  registries and git sources are denied.

CI runs this check on pushes and pull requests. Dependabot opens weekly updates
for Cargo dependencies and GitHub Actions. Many CI actions are pinned to full
commit SHAs with a version comment; the release binary jobs still use a few
major-version action tags (for example `actions/checkout@v5`). Treat the
workflow file as the source of truth rather than assuming every action is
SHA-pinned.

This policy reduces supply-chain risk; it does not make the project
reproducible-build-verified. The release binaries are built by GitHub Actions
from the tagged commit, and the attestation records that build. The project
does not publish a reproducible-build proof or a bit-for-bit independent
rebuild.

## Reporting a supply-chain problem

If a published artifact does not match its checksum or attestation, or a
dependency issue affects the scanner, report it privately following
[`SECURITY.md`](../SECURITY.md). Do not open a public issue with an unreported
exploit.
