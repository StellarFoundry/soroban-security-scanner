# SS-044 - Cross-contract call with an unvalidated address argument

- **Severity:** medium
- **Confidence:** low
- **Category:** cross-contract

## Problem

A cross-contract token call receives an address argument whose value comes from a
caller-supplied parameter. Unless the contract validates that address, the caller
chooses the destination of a transfer, approval, mint, burn, or clawback. If the
address is not the account or contract the operation expects, funds can move to
the wrong party or the call can fail in an unexpected way.

## How it is detected

For every public `#[contractimpl]` entry point, the detector runs the shared
privileged-address taint analysis (`analysis::taint::address_argument_flows`).
That analysis seeds every non-`Env` parameter as caller-controlled and follows
assignments, references, casts, free-function calls, and intra-file helpers to a
fixed point. The privileged sinks are the documented token call positions:
`transfer` (recipient), `transfer_from` (from, to), `approve` (spender),
`mint`/`burn`/`clawback` (subject), and `burn_from` (from).

A finding requires a concrete path (`Direct`, `Alias`, or `Transformed`) to an
address argument that was not passed through one of the documented sanitizers:
`validate_address`, `normalize_address`, `checked_address`, `verified_address`,
or `sanitize_address`. The evidence names the call, the argument position, the
source path, and the entry function.

## Ambiguity is not reported

`TaintPath::Unknown` means the analysis could not establish a single origin, for
example because validation only happens inside an `if` branch or because a value
has more than one tainted source. This rule deliberately skips those flows
instead of guessing. Unconditional validation, a stored address, or a literal
address also produces no finding.

## Limitations

- Syntactic and per entry point. Cross-file helpers, macros, trait dispatch, and
  type inference are not followed.
- Privileged calls are matched by method name and fixed argument index, with no
  receiver-type check. An unrelated method with the same shape can produce a
  flow; the evidence includes the call and location for review.
- Only the documented sanitizer names clear the flow. A different validation
  helper does not, and an `Address` type annotation is never treated as
  validation.
- A conditional guard such as `if amount > 0` is not address validation and does
  not clear the flow.
- The rule reports low confidence because a caller-supplied recipient can be
  legitimate for permissionless withdrawal or payment contracts; review the
  evidence.

## False positives

- A payment contract that intentionally lets the caller choose the recipient.
- Validation performed in another contract or outside the analyzed file.
- An unrelated method named `transfer`, `approve`, or `mint` on a non-token type.

## Remediation

Validate the address on every path before the call. Use a documented helper,
compare against configuration stored when the contract was initialized, or
reject addresses that are not on an explicit allowlist.

```rust
pub fn payout(env: Env, token_id: Address, to: Address, amount: i128) {
    let recipient = validate_address(&env, to);
    let client = token::Client::new(&env, &token_id);
    client.transfer(&env.current_contract_address(), &recipient, &amount);
}
```

`validate_address` must actually fail closed for addresses the contract does not
accept; the rule only recognizes the documented helper name.
