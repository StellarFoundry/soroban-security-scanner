# SS-021 — Durable data written to temporary storage

- **Severity:** medium
- **Confidence:** low
- **Category:** storage

## Problem

Temporary storage entries are removed when their TTL lapses. Storing data that is
meant to persist — configuration, balances, or ownership — in temporary storage
can make it silently disappear, breaking the contract.

## How it is detected

For every public `#[contractimpl]` entry point, the detector collects
`temporary().set(...)` calls (and the UFCS form `Temporary::set(...)`). It reports
when the rendered key expression contains a durable-state hint such as `owner`,
`admin`, `balance`, `allowance`, `config`, `metadata`, or `supply`.

## Limitations

- Key names are a heuristic; a durable key with an unusual name is missed.
- A durable key written through a differently named local variable may not be
  resolved to temporary storage.
- Helpers are not traced.

## False positives

- Ephemeral keys that happen to contain a hint word (for example a session
  nonce named `config_version`).
- Temporary data that is intentionally short-lived for values named like
  configuration.

## Remediation

Write durable state to persistent (or instance) storage. Use temporary storage
only for data that may safely be discarded, and extend its TTL when it is still
needed.

```rust
env.storage().persistent().set(&DataKey::Owner, &owner);
```
