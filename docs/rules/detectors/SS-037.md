# SS-037 — Competing authorization calls on distinct actors

- **Severity:** medium
- **Confidence:** low
- **Category:** authorization

## Problem

When a single contract entry point calls `require_auth` or
`require_auth_for_args` on two or more distinct actor receivers (for example,
both `admin.require_auth()` and `user.require_auth()`), it usually signals
confused authorization semantics or an unintended requirement that two
unrelated parties co-sign a single transaction. If either actor is unavailable
or refuses to sign, the operation cannot proceed.

## How it is detected

For each public function in a `#[contractimpl]` block, the detector collects all
`require_auth` and `require_auth_for_args` method calls, normalizes their
rendered receiver text (stripping whitespace and leading `&` / `mut`), and
reports a finding when two or more distinct receivers appear in the same entry
point.

## Limitations

- Receiver comparison is syntactic: aliases pointing to the same `Address`
  under different variable names are treated as distinct receivers.
- Authorization delegated to helper functions outside the entry point block is
  not merged.

## False positives

- Legitimate multi-party flows such as atomic two-party swaps or inline
  co-signing where two named actors must authorize a single call.
- Documented multi-signature patterns typically avoid competing receivers in a
  single entry point by either recording individual signer approvals via a
  proposal/approval state machine (`approve(env, signer, proposal_id)`) or
  iterating over a deduplicated `Vec<Address>` of signers.

## Remediation

Split administrative and user operations into separate entry points with a
single authorizing actor per function, or use a dedicated multi-sig approval
workflow.

```rust
pub fn approve_proposal(env: Env, signer: Address, proposal_id: u64) {
    signer.require_auth();
    // record signer approval for proposal_id
}
```
