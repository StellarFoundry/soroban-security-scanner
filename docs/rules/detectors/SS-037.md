# SS-037 - Competing authorization calls

- **Severity:** medium
- **Confidence:** low
- **Category:** authorization

## Problem

A single contract entry point calls `require_auth` for two or more distinct
actors. Multiple separate approvals in one operation usually indicate confused
authorization semantics: it becomes unclear which actor the operation is really
gated on, and a missing or misplaced check elsewhere may be masked by the
additional approvals. Attackers can sometimes exploit the mismatch between the
actor a reviewer assumes is authorized and the actor the code actually requires.

Legitimate multi-party flows exist, so this rule reports low confidence and each
finding must be reviewed in context.

## How it is detected

The detector visits public functions in `#[contractimpl]` blocks. It collects the
rendered receiver of every `require_auth` and `require_auth_for_args` call and
reports once per entry point when at least two distinct receivers are authorized.

Repeated authorization for the same receiver, and entry points that authorize a
single actor, are not reported.

## Limitations

- It compares rendered receiver text. Two aliases for the same underlying address
  are treated as distinct actors, and the same textual receiver is treated as one
  actor even if it resolves differently at runtime.
- It does not follow helper functions, so authorizations performed in helpers are
  not counted.
- It cannot determine whether the multi-actor flow is intentional and correct.
- It reports one finding per entry point, not one per additional actor.

## False positives

- Documented multi-party flows, such as a settlement that genuinely requires both
  counterparties to approve.
- A single Stellar multisig account, where the network enforces the signing
  policy, is one actor and is not reported even when the account is authorized
  more than once.

## Remediation

Prefer a single, explicit authorization for the actor whose operation this is, or
bind every required party through one documented multi-sig pattern. If a flow
genuinely requires several independent approvals, document the policy and add a
justified inline suppression:

```rust
// soroban-scan: ignore SS-037 -- both counterparties must approve settlement
from.require_auth();
to.require_auth();
```
