# SS-032 — Redundant require_auth call inside a loop

- **Severity:** low
- **Confidence:** low
- **Category:** resource-usage

## Problem

Invoking `require_auth` or `require_auth_for_args` inside a `for`, `while`, or
`loop` body repeats an expensive Soroban host authorization check on every
iteration. When the receiver is a single caller or administrator address, the
repeated check wastes CPU instructions and host-call budget without adding
security; when the receiver is a loop element, an unbounded or duplicate-heavy
batch can exhaust transaction resources or fail unexpectedly unless the batch
is bounded and deduplicated first.

## How it is detected

For each public function inside a `#[contractimpl]` block, the AST visitor
tracks lexical loop depth across `for`, `while`, and `loop` expressions and
records every `require_auth` or `require_auth_for_args` method call that occurs
inside a loop body.

## Limitations

- Calls inside helper functions invoked from a loop body are not flagged unless
  the loop construct itself is inside the analyzed function.
- Closures passed to iterator combinators (such as `.for_each(...)`) are not
  treated as lexical loop blocks.

## False positives

- Multi-party batch operations that intentionally call `require_auth` on each
  distinct participant in a small, bounded list. Even in those cases,
  deduplicating participant addresses or hoisting caller authorization outside
  the loop is recommended.

## Remediation

Hoist `require_auth()` or `require_auth_for_args(...)` out of the loop body so
authorization is verified once before iterating over the batch.

```rust
pub fn distribute(env: Env, admin: Address, recipients: Vec<Address>, amount: i128) {
    admin.require_auth();
    for recipient in recipients.iter() {
        env.storage().persistent().set(&recipient, &amount);
    }
}
```
