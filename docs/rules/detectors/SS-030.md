# SS-030 — Token client constructed from unvalidated Address parameter

- **Severity:** high
- **Confidence:** low
- **Category:** token

## Problem

A state-changing contract entry point constructs a token client
(`token::Client::new` or `TokenClient::new`) from a caller-supplied `Address`
parameter without comparing it against a stored token address or allowlist. An
attacker can pass a malicious or worthless token contract to credit real
protocol balances or hijack execution via a fake token.

## How it is detected

Within a public `#[contractimpl]` entry point that mutates storage, the
detector inspects `*Token*Client::new` and `token::Client::new` calls whose
address argument references a function parameter and reports those that have no
comparison or storage allowlist lookup (`has`, `get`, `contains`) involving
that parameter.

## Limitations

- Allowlist validation performed inside a helper function is not tracked.

## False positives

- Permissionless multi-token registries where any token address is intentionally
  accepted and isolated by `(token, user)` composite storage keys.

## Remediation

Load the accepted token contract `Address` from contract storage (or verify
membership in an allowlist) before constructing `token::Client::new` in
state-changing entry points.
