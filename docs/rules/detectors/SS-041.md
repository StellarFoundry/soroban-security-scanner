# SS-041 - Authorization check inside a loop

- **Severity:** medium
- **Confidence:** medium
- **Category:** authorization

## Problem

A contract entry point performs `require_auth` (or `require_auth_for_args`)
inside a loop body in a position that does not clearly cover every iteration.
When the check is conditional, iterations that skip the branch run
unauthenticated. When the check runs only after a state-changing operation,
earlier side effects happen without authorization. A single check in either
position may be insufficient for the whole loop.

## How it is detected

The detector visits public functions in `#[contractimpl]` blocks and tracks the
lexical nesting of `for`, `while`, and `loop` expressions. It reports a
`require_auth` or `require_auth_for_args` call inside a loop when either:

- the call is nested inside an `if` or `match` within the loop, or
- a storage mutation or cross-contract call is positioned before the
  authorization call in the same loop.

The evidence names the enclosing loop kind, its line, the entry point, and why a
single check may be insufficient.

## Limitations

- This is a syntactic check. It cannot prove which actor or argument set is
  authorized on each iteration.
- Unconditional checks at the top of a loop are deliberately not reported:
  whether they are sufficient or redundant depends on context. SS-032 covers the
  resource-efficiency concern separately.
- Side effects are recognized by storage method names and common cross-contract
  method names; calls through unusual adapters may be missed.
- Closures and macro-generated loops or authorization calls are not inspected.

## False positives

- A conditional check that is intentionally applied to only some iterations and
  documented with an inline suppression.
- A storage mutation that is logically unrelated to the authorized operation and
  intentionally happens first (for example a reentrancy marker).

## Remediation

Authorize before any state change and outside branches that can skip iterations,
or authorize each distinct actor explicitly:

```rust
admin.require_auth();

for recipient in recipients.iter() {
    transfer(&env, &recipient, &amount);
}
```

If every iteration genuinely authorizes a different actor, use
`require_auth_for_args` with the complete argument set and document why.
