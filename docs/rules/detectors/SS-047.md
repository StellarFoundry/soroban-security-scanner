# SS-047 - Unchecked ledger timestamp usage

- **Severity:** medium
- **Confidence:** low
- **Category:** arithmetic

## Problem

A contract compares the ledger timestamp with a deadline without allowing any
tolerance:

```rust
let now = env.ledger().timestamp();
if now >= deadline {
    // close the auction
}
```

Ledger time is not a precise wall clock chosen by the contract. The network
selects a close time within protocol bounds, and a transaction can execute in a
later ledger than the one the user observed. A zero-slack comparison therefore
flips on a boundary that the contract does not control. For an auction close,
a vesting cliff, or a refund deadline, that can let a transaction succeed one
ledger early or fail one ledger late.

The safe pattern is an explicit, documented window such as
`now.saturating_sub(deadline) <= CLOSE_WINDOW`.

## How it is detected

The detector examines public `#[contractimpl]` entry points and their
comparison facts. It follows simple local aliases initialized from
`ledger().timestamp()`, so both of these are considered timestamp comparisons:

```rust
if env.ledger().timestamp() >= deadline { }
let now = env.ledger().timestamp();
if now >= deadline { }
```

Only ordered comparisons (`<`, `<=`, `>`, `>=`) are reported. Equality is not
treated as a deadline check.

## Ambiguity is not reported

The rule suppresses a function when any of the following is visible:

- the comparison mentions a tolerance-style name such as `tolerance`, `window`,
  `slack`, `grace`, `skew`, `margin`, or `buffer`;
- the function uses `checked_add`, `checked_sub`, `saturating_add`, or
  `saturating_sub`, which bound the arithmetic by construction;
- the timestamp is only read, returned, or compared with a non-timestamp value.

Suppression is function-wide on purpose. A bounded window elsewhere in the same
entry point may cover the comparison, and guessing otherwise would fabricate a
finding.

## Limitations

- The detector does not evaluate constants, so a tolerance stored in a constant
  whose name does not contain a tolerance word is not recognized.
- It follows simple `let` aliases only. Timestamps loaded from storage and
  passed through function calls are not traced.
- It does not prove that the ledger timestamp is security-critical; a
  informational timestamp is reported the same as a settlement deadline.
- A tolerance window that is present but too small is not measured.
- Low confidence is intentional: the rule sees the comparison, not the
  contract's timing model.

## False positives

- A comparison whose tolerance is named `MARGIN` or `BUFFER` and therefore
  matches a suppression hint.
- A timestamp comparison that only chooses a log message or an event value.
- A comparison against a timestamp that is not used for authorization or value
  transfer.

## Remediation

Name the window and compare within it:

```rust
const CLOSE_WINDOW: u64 = 5; // ledgers, justified by the timing model

let now = env.ledger().timestamp();
if now.saturating_sub(deadline) <= CLOSE_WINDOW {
    // close the auction
}
```

Keep the window as small as the use case allows and document why it is safe.
