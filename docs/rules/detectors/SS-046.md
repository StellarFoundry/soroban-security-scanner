# SS-046 - Duplicate storage key construction

- **Severity:** medium
- **Confidence:** low
- **Category:** storage

## Problem

Two logical records are written through the same storage key construction, so
one record can overwrite or be read as the other. A typical shape is:

```rust
env.storage().persistent().set(&DataKey::Balance(user.clone()), &Balance { amount });
// later
env.storage().persistent().set(
    &DataKey::Balance(user.clone()),
    &Balance { amount, unlock_at },
);
```

The key does not say which record shape it holds. If both records are live at
the same time, the second write destroys the first, and a reader cannot tell
which shape it will find. Storage collisions are a correctness and availability
problem: they can silently reset balances, roles, or deadlines.

## Why this rule exists

Soroban storage is a flat map from an encoded key to a value. Nothing validates
that the value stored under a key keeps one shape. When a contract reuses a
literal or a partially distinguishing constructor for different records, the
compiler cannot detect the clash and tests that cover only one path will not
notice it. Namespacing the key is the durable fix.

## How it is detected

The detector visits every function inside a `#[contractimpl]` block and collects
`set(key, value)` calls whose receiver is a storage chain. For each call it
records:

- the storage class (`persistent`, `temporary`, or `instance`),
- the key expression exactly as written, and
- the field set of a struct-literal value, such as `{amount}` or
  `{amount, unlock}`.

It reports when the same storage class and key expression are used with two
different non-empty struct field sets. The finding points at the later key
construction and names both field sets.

## Ambiguity is not reported

The rule is deliberately narrow:

- Values that are not struct literals (scalars, paths, calls, tuples) have no
  visible field set, so they never trigger the rule.
- A struct literal using `..rest` has an unknown final field set and is skipped.
- The same field set is one record shape, even when the values differ.
- Different key expressions are different namespaces, even if their value
  fields differ.
- The same key text in different storage classes cannot collide and is not
  reported.
- Calls outside `#[contractimpl]` blocks are ignored.

## Limitations

- The key comparison is syntactic. `DataKey::Balance(user)` and
  `DataKey::Balance(user.clone())` are treated as different expressions even
  when they encode the same key.
- Struct literals inside macros or behind type aliases are not inspected.
- A collision between a value written by this file and a value written by
  another file or a dependency is not visible.
- Only `set` is inspected. `update`, `extend_ttl`, and direct host calls are not
  compared.
- Low confidence is intentional: a shared key can be legitimate during a
  migration or when the contract guarantees that only one shape is ever live.

## False positives

- A key that intentionally stores a versioned enum whose variants have different
  fields.
- Migration code that rewrites the same key from an old shape to a new shape and
  never keeps both shapes live.
- Different value shapes guarded by an explicit version discriminator in the
  value.

If a shared key is intentional, document the invariant and suppress the rule for
that location.

## Remediation

Give every logical record its own namespaced key:

```rust
pub enum DataKey {
    Balance(Address),
    BalanceLock(Address),
}

env.storage().persistent().set(&DataKey::Balance(user), &amount);
env.storage().persistent().set(&DataKey::BalanceLock(user), &unlock_at);
```

If the records must share a key, store one explicitly versioned value type and
migrate it atomically.
