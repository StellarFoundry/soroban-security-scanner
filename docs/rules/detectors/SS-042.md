# SS-042 - Security check unreachable on every path

- **Severity:** low
- **Confidence:** medium
- **Category:** authorization

## Problem

A caller-authorization or validation check appears after a statement that always
leaves the function, such as an unconditional `return`. No execution path reaches
the check, so the contract behaves as if the guard were absent while the source
suggests the operation is protected. Dead security checks are a source of false
confidence in review.

## How it is detected

The detector builds the per-function control-flow graph (CFG) for every public
function in a `#[contractimpl]` block and looks for call sites named
`require_auth`, `require_auth_for_args`, or a documented validation helper with a
`validate_`, `verify_`, `check_`, or `ensure_` prefix. A call is reported only
when `reachability_at(line)` proves it `Unreachable`.

The finding is suppressed entirely when the graph is incomplete:
`ControlFlowGraph::truncated` is set, or the graph contains any `NodeKind::Unknown`
node. Macros, closures, `break`/`continue`, and other unmodelled constructs create
`Unknown` nodes, so a check in such a function is never guessed to be dead.

The evidence names the check, the function, the nearest preceding `return` line,
and the graph size, for example:

```text
`require_auth` check at line 9 in `set` is unreachable: every path leaves the
function first (nearest `return` at line 8); CFG is complete (5 nodes, 5 edges,
no unknown nodes)
```

## Limitations

- Detection is limited to the modelled CFG. A construct the builder does not
  model suppresses the finding rather than producing a guess.
- Only public `#[contractimpl]` functions are inspected; dead checks in private
  helpers are not reported.
- Check names are matched syntactically. The rule does not resolve types and
  cannot prove that `validate_*` validates anything.
- Macro-based checks (`assert!`, `panic!`) become `Unknown` nodes, so this rule
  intentionally never reports them.
- Line-granular spans cannot distinguish two constructs that share a line.

## False positives

- A check deliberately kept as documentation or for a future code path. Review
  the finding and suppress it with a justified inline directive if the dead code
  is intentional.
- A method named like a validation helper that is not security relevant.

## Remediation

Move the check before the early return, or fold it into the condition that
returns:

```rust
admin.require_auth();
if stop {
    return;
}
env.storage().persistent().set(&admin, &1);
```

Delete dead checks that are no longer intended.
