# SS-036 — Deprecated Soroban SDK API usage

- **Severity:** low
- **Confidence:** medium
- **Category:** dependencies

## Problem

Contracts that call Soroban SDK APIs removed or superseded in newer SDK
releases may fail to compile on upgrade or carry stale security assumptions
(for example, single-parameter TTL bumping without a threshold, raw `BytesN<32>`
contract IDs instead of `Address`, or deployment helpers that bypass
`__constructor` initialization).

## How it is detected

In confirmed Soroban projects, the detector walks parsed Rust ASTs (`ExprMethodCall`
and `ExprCall`) and matches calls against a versioned, data-driven table of
deprecated Soroban SDK APIs (`DEPRECATED_SDK_APIS`). When `Cargo.toml` manifests
are available, only entries deprecated at or before the project's detected
`soroban-sdk` version are active; when scanning standalone source files without
a manifest, all table entries are checked.

### Versioned deprecated API table

| Deprecated API | Deprecated / Replaced In | Replacement | Rationale |
| -------------- | ------------------------ | ----------- | --------- |
| `storage().<tier>().bump` | `20.0.0` | `storage().<tier>().extend_ttl(threshold, extend_to)` | Replaced by `extend_ttl` with explicit threshold and extension ledgers to prevent silent TTL under-extension. |
| `Env::current_contract_id` | `20.0.0` | `Env::current_contract_address` | Raw `BytesN<32>` contract identifiers were replaced by unified `Address` values. |
| `Address::from_contract_id` | `20.0.0` | `Address::from_str(&env, ...)` or direct `Address` parameters | Legacy contract ID conversion was removed when `Address` unified account and contract identities. |
| `Deployer::with_source_account` | `20.0.0` | `Deployer::with_address(address, salt)` | Deployer source-account scoping was generalized to any `Address` via `with_address`. |
| `Env::register_contract` | `22.0.0` | `Env::register(contract, constructor_args)` | `register_contract` bypasses `__constructor` argument passing introduced in SDK 22. |
| `Env::register_contract_wasm` | `22.0.0` | `Env::register(wasm, constructor_args)` | `register_contract_wasm` was superseded by `Env::register` with constructor support in SDK 22. |
| `DeployerWithAddress::deploy` | `22.0.0` | `DeployerWithAddress::deploy_v2(wasm_hash, constructor_args)` | `deploy` does not pass contract constructor arguments; `deploy_v2` is required from SDK 22 onward. |

## Limitations

- Matching is syntactic over AST call and method-call expressions without full
  type resolution (`rustc` / `hir`).
- Custom user types that define methods with identical receiver shapes (such as
  a custom `storage().bump()` helper unrelated to Soroban storage) may match.

## False positives

- User-defined domain structs that expose a method named `bump` on a receiver
  expression containing `storage(...)` or `register_contract` on a custom `env`
  wrapper.
- Contracts intentionally pinned to an older `soroban-sdk` version when scanned
  as standalone `.rs` files without their `Cargo.toml` manifest.

## Remediation

Migrate each flagged call to its modern SDK replacement shown in the table
above:

```rust
// Before (deprecated):
env.storage().persistent().bump(&key, 100, 1000);
let self_id = env.current_contract_id();

// After (modern):
env.storage().persistent().extend_ttl(&key, 100, 1000);
let self_addr = env.current_contract_address();
```
