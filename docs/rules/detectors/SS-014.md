# SS-014 — Token transfer amount without validation

- **Severity:** medium
- **Confidence:** low
- **Category:** token

## Problem

A contract entry point forwards a caller-supplied `amount` to `transfer` or
`transfer_from` without checking it against zero. Token implementations differ
in how they handle negative or out-of-range values: some wrap, some panic, and
some apply their own policy. Relying on the callee to reject a bad amount makes
the caller's accounting and error handling depend on external behaviour, and a
missing guard is a common source of unintended transfers and broken balances.

## How it is detected

For every public function inside a `#[contractimpl]` block, the detector looks
for `transfer` and `transfer_from` calls whose **last argument** is a reference
to a simple function parameter (for example `&amount`). The finding is reported
unless the same function contains an inequality comparison between that
parameter and the integer literal zero, such as:

```rust
if amount <= 0 {
    return Err(Error::InvalidAmount);
}
```

Both operand orders are accepted (`amount > 0` and `0 < amount`), and the guard
may appear inside an `if`, `assert!`, or any other expression in the function.
Comparisons against non-zero literals do not count as a guard.

## Limitations

- Purely syntactic; there is no type, range, or data-flow analysis. The detector
  cannot prove that the amount is attacker-controlled or that the transfer is
  reachable with an invalid value.
- Only direct `transfer`/`transfer_from` calls are inspected. Transfers performed
  inside private helpers are not followed, and custom token wrappers with other
  method names are not recognized.
- The amount must be the **last** argument and a plain identifier. A transfer
  whose amount is a literal, a computed expression, or a value read from storage
  is ignored.
- A zero comparison anywhere in the function suppresses the finding, even if it
  does not dominate the transfer on every path.

## False positives

- The caller validates the amount in a different function or before calling this
  entry point.
- The token itself enforces a positive-amount invariant and the contract
  deliberately forwards the value.
- An unrelated comparison against zero in the same function (for example a
  different parameter) suppresses the finding.

## Remediation

Validate the amount before transferring and return a typed contract error:

```rust
if amount <= 0 {
    return Err(Error::InvalidAmount);
}
```

For tokens with an upper bound, check both ends of the range. Validate once at
the entry point and pass the checked value to `transfer` or `transfer_from`.
