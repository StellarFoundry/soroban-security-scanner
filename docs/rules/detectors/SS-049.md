# SS-049 - Unchecked bytes-to-string conversion

- **Severity:** medium
- **Confidence:** high
- **Category:** error-handling

## Problem

A public entry point converts caller-supplied bytes to text and unwraps the
result:

```rust
#[contractimpl]
impl Contract {
    pub fn set_name(env: Env, bytes: Bytes) {
        let name = String::from_utf8(bytes).unwrap();
        env.storage().persistent().set(&Key::Name, &name);
    }
}
```

`String::from_utf8` returns a `Result` because not every byte sequence is valid
UTF-8. `unwrap()` and `expect(...)` turn that recoverable error into a panic. A
caller can therefore abort the contract call with a crafted argument, and a
panic in one entry point can take down a transaction that would otherwise be
handled as a normal contract error.

`String::from_utf8_unchecked` is worse: it produces a `String` without
validating the bytes, so the contract can build a value with undefined contents.

## How it is detected

The detector examines public `#[contractimpl]` entry points and reports two
forms:

- `from_utf8(...)` followed by `.unwrap()` or `.expect(...)`, for both
  `String::from_utf8(bytes)` and `std::str::from_utf8(&bytes)`;
- a direct call to `from_utf8_unchecked(...)`.

The evidence is the converted expression and the panic or unchecked call. The
rule does not fire on checked handling such as `?`, `match`, `unwrap_or`, or
`unwrap_or_default`, and it does not fire on `from_utf8_lossy`, which replaces
invalid sequences instead of failing.

## Limitations

- The conversion and the unwrap must be visible in the same expression. A
  `Result` stored in a local and unwrapped several statements later is not
  followed.
- It does not trace bytes through helpers, storage, or cross-contract calls; the
  panic potential is reported from the conversion site itself.
- It does not prove that the bytes are caller-controlled. A `from_utf8` on a
  compile-time constant that is unwrapped is reported the same way.
- Only public entry points are inspected. A private helper that panics is
  ignored, even when an entry point calls it.
- The `.unwrap()`/`.expect(...)` chain is matched syntactically, so an aliased
  `Result` helper is not recognized.

## False positives

- `String::from_utf8(bytes).map_err(|_| Error::InvalidUtf8)?`.
- A `match` on the conversion result that returns a contract error.
- `from_utf8_lossy`, which cannot fail.
- `unwrap_or_default` or `unwrap_or(fallback)`, which replace the error.
- A conversion performed only in a private helper or in `#[cfg(test)]` code.

## Remediation

Handle the error and return a contract error:

```rust
let name = String::from_utf8(bytes).map_err(|_| Error::InvalidUtf8)?;
env.storage().persistent().set(&Key::Name, &name);
```

Match the `Result` when different errors need different handling, and never use
`from_utf8_unchecked` on bytes that a caller can influence.
