# SS-028 — Cross-contract call without a reentrancy guard

- **Severity:** high
- **Confidence:** low
- **Category:** cross-contract

## Problem

Soroban permits reentrancy. An entry point that calls another contract and then
mutates its own storage can let a malicious callee re-enter while state is
inconsistent, observing or exploiting a half-applied update.

## How it is detected

For every public `#[contractimpl]` entry point, the detector orders
cross-contract calls and storage mutations. It reports a cross-contract call that
precedes a storage mutation when no guard is visible. A guard is a storage flag
whose key looks like a lock (`lock`, `guard`, `entered`, `reentr`, `busy`) that
is both read (`get`) and set (`set`) before the call.

## Limitations

- Purely syntactic ordering within one function; helpers are not traced.
- Only direct client calls and constructors are recognized.
- A guard implemented without storage (for example a host primitive or an
  external module) is not recognized.

## False positives

- Flows that are safe because the callee cannot re-enter or the intermediate
  state is harmless.
- Guards that do not use a recognizably named storage key.

## Remediation

Set a lock flag before the external call and clear it after, or follow
checks-effects-interactions and finish all state updates first.

```rust
let locked: bool = env.storage().persistent().get(&Key::Locked).unwrap_or(false);
if locked {
    panic!("reentrant");
}
env.storage().persistent().set(&Key::Locked, &true);
let client = token::Client::new(&env, &token);
client.transfer(&env.current_contract_address(), &to, &amount);
env.storage().persistent().set(&Key::Locked, &false);
```
