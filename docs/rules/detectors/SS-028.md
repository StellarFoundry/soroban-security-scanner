# SS-028 — State mutation after cross-contract call without reentrancy guard

- **Severity:** high
- **Confidence:** low
- **Category:** cross-contract

## Problem

A public contract entry point mutates contract state (`set`, `update`, or
`remove`) after an external cross-contract invocation without acquiring a
reentrancy lock. If the remote contract re-enters before the post-call write
completes, it can observe or corrupt intermediate state.

## How it is detected

Within a public `#[contractimpl]` entry point, the detector reports storage
writes (`set`, `update`, `remove`) that occur after a cross-contract client
call when no reentrancy lock/guard identifier (`lock`, `reentrancy`,
`reentrant`, `entered`, `guard`, `in_progress`, `mutex`) appears in the
function's call expressions.

## Limitations

- Guard acquisition inside a macro or external helper module is not resolved.

## False positives

- Calls to trusted, non-reentrant system contracts where post-call accounting is
  safe.

## Remediation

Apply all state mutations before invoking external contracts
(checks-effects-interactions), or protect the entry point with an explicit
reentrancy guard.
